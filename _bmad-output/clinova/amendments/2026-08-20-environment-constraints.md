# Amendment — Environment constraints discovered starting Phase 0

Recorded live during Phase 0 kickoff, per this project's own convention of dating findings rather than silently rewriting prior artifacts (matching the inherited baseline project's `deferred-work.md` style).

## What was found

- This machine (a company laptop) has **no local administrator rights** in this session (`whoami /groups` confirms not in `Administrators`; `Get-WindowsOptionalFeature` fails with "requires elevation").
- **WSL2 is not installed**, and installing it requires elevation this session doesn't have.
- **Docker Desktop cannot be installed** in this session as a result — it needs either the Hyper-V backend or WSL2, both gated behind admin rights.
- A `winget install Python.Python.3.11` attempt (non-elevated) was **silently cancelled by the installer itself** ("You cancelled the installation", exit 1602) — consistent with the same admin-rights restriction, since the python.org all-users installer triggers a UAC prompt that a non-interactive elevated session can't answer. A `--scope user` retry (which installs per-user, no elevation needed) was in progress when this amendment was written.
- **Java 11 (Microsoft OpenJDK, `jdk-11.0.16.101-hotspot`) is already installed** and on `PATH` — likely provisioned by IT for other tooling. This is materially useful: GROBID can run as a plain Java service via its Gradle build (`./gradlew run`), with no Docker dependency at all.

## Decisions (interim, until Docker access is resolved or confirmed unavailable long-term)

1. **Phase 1's multi-parser combination is temporarily two parsers, not three:** PyMuPDF (existing, pure Python) + **Docling** (pure pip-installable Python package, no Docker/JVM dependency — unaffected by this constraint). GROBID is **deferred**, not dropped — `05-data-architecture.md` §2's recommendation of GROBID+PyMuPDF+Docling stands as the target combination; only the sequencing changes.
2. **GROBID has a viable non-Docker path**, newly confirmed: build and run it directly via Gradle against the already-installed Java 11 (`./gradlew run`, no Docker/admin rights required — GROBID's Gradle build runs entirely in user space). This is **not attempted in this session** because it's a heavy, slow operation (cloning a large repo, a long first build, downloading pretrained citation-parsing models) that deserves a deliberate pass with disk-space/time awareness, not a side effect of unblocking Phase 0. Recorded here as the confirmed unblock path for whenever Phase 1's Epic 1.1 GROBID work is picked up.
3. **`08-local-deployment-architecture.md`'s `data` Compose profile assumption is revised for the interim:** Docling runs as a plain local Python dependency (no container). GROBID, when picked up, runs via Gradle directly rather than via the `data` Compose profile's Docker service — the Compose profile still applies once/if Docker access is later resolved (e.g., IT provisions it, or this work moves to a machine with admin rights), at which point this amendment is superseded, not deleted.
4. **Python 3.11 is being installed per-user** (`winget install --scope user`, no admin required) rather than via the devcontainer's all-users assumption — functionally equivalent for this project's purposes (a venv either way), just scoped to the current user profile instead of system-wide.

## What this does NOT change

- No architecture decision (ADR-001 through ADR-008) is affected — this is a local development-environment workaround, not a product architecture change.
- `05-data-architecture.md`'s target parser combination (GROBID + PyMuPDF + Docling) is unchanged as the eventual target; only *when* GROBID specifically is stood up is affected.
- Story 1.1.1 (`09-epics-and-stories.md`) is revised in place: its acceptance criteria now target the Gradle-based GROBID path instead of the Docker `data` profile, and are deferred to a dedicated pass rather than blocking the rest of Epic 1.1.

**Resolved, 2026-08-22 — Neo4j replaced by ArcadeDB, not worked around:**
- ~~Neo4j CE (Phase 3, Epic 3.1 — Graph Persistence & Quality Scoring)~~ **The user decided against ever setting up Neo4j and asked for an open-source, no-Docker alternative instead of continuing to wait on Docker access.** [ArcadeDB](https://arcadedb.com) (Apache 2.0, actively maintained, speaks the same openCypher this project's docs already reference for Neo4j) runs as a plain local JVM process — no Docker, no admin rights, using the exact same "portable per-user install" pattern already established for Python 3.11 and planned for GROBID. Set up live this session: downloaded portable Eclipse Temurin JDK 21 (this machine only had Java 11, and ArcadeDB requires 21+) and the ArcadeDB 26.8.1 base distribution, both extracted to `C:\Users\Divya\tools\` with no installer. Started via `bin\server.bat` with `JAVA_OPTS=-Darcadedb.server.rootPassword=<password>` to skip the interactive first-run prompt (which hangs in a non-interactive session). Confirmed working end-to-end: HTTP API reachable, real vertex/edge writes, a real openCypher `MATCH` query returning the correct result.
- New `pipeline/graph_persistence.py` implements Epic 3.1's actual requirement (cross-run graph persistence -- comparing graphs across separate runs, which the existing in-memory single-run graph genuinely can't do) via ArcadeDB's HTTP API (`requests`, already a dependency -- no new Python package). Two real bugs found live and fixed: `DELETE VERTEX` needs a `FROM` keyword ArcadeDB's docs don't make obvious, and dereferencing an edge's connected-vertex property needs the `@`-prefixed `@out.field`/`@in.field` form -- the unprefixed form silently returns null instead of erroring. Both locked in with regression tests. Live-verified with two real saved runs from the same corpus family: saved both (96 and 61 entities), reconstructed one back byte-for-byte, and diffed them correctly (61 entities/relationships common to both, 34-35 unique to the larger 3-paper run -- exactly the expected shape given one run's corpus is a superset of the other's). Full detail in RESUME.md.
- **The server is a real, separate local process you now need to start manually before using this feature** (`JAVA_HOME=<path to the extracted JDK 21>; JAVA_OPTS=-Darcadedb.server.rootPassword=<your password>; bin\server.bat`, run from inside the extracted ArcadeDB distribution directory) -- nothing else in the pipeline depends on it, so everything else keeps working with it stopped.
- **Wired into `app.py`'s UI and live-verified via Playwright, 2026-08-22** (checkbox + save-on-completion + a cross-run diff panel). Verification surfaced a real, unrelated gap: `app.py` never loaded `.env` at all -- fixed with the same minimal loader already used across `evals/benchmarks/baseline/*.py`. Full detail in RESUME.md.

**Resolved, 2026-08-22 — Qdrant replaced by NVIDIA NIM hosted embedding/reranking, not worked around:**
- ~~Qdrant (Phase 3, Epic 3.5 — EmbeddingProvider/RerankerProvider)~~ **The user asked directly why this wasn't just using the NVIDIA API, same as every other AI call in this app.** Right call: this machine has no GPU, so 04-ai-research-architecture.md's original "BGE-M3/BGE-reranker, local" port-table note would have meant slow CPU-only inference plus large local model downloads. NVIDIA NIM already hosts equivalent embedding/reranking models on the same `integrate.api.nvidia.com`/`ai.api.nvidia.com` endpoints this app already calls, using the same `NVIDIA_API_KEY` already in `.env` — zero new credentials, zero local model downloads. New `pipeline/relevance_ranking.py` implements `embed_texts()`/`rerank_candidates()` via plain HTTP (`requests`, already a dependency) and the existing `openai` client. No vector database is used or needed: Gap Challenger's candidate pool per gap challenge is Semantic Scholar/arXiv results for a handful of query families — tens of candidates, not a corpus to index against. NVIDIA's rerank endpoint scores query-passage relevance directly; there's nothing here for a persistent ANN vector store to do at this scale.
- **Real bugs found live, not assumed from docs — three in a row, worth remembering next time a model name is picked from a docs page instead of tested:** `nvidia/llama-3.2-nv-rerankqa-1b-v2` and `nvidia/llama-3.2-nv-embedqa-1b-v2` (the models named in NVIDIA's own model-card pages) both live-returned HTTP 410 Gone ("reached end of life" 2026-05-18), and the next embedding model tried (`llama-3.2-nemoretriever-300m-embed-v2`) also 410'd (EOL 2026-02-26) — all three despite their docs pages showing no deprecation notice. Resolved by querying `GET /v1/models` (the real, current catalog) and live-testing candidates directly: `nvidia/llama-nemotron-embed-1b-v2` (2048-dim, confirmed) and `nvidia/llama-nemotron-rerank-1b-v2` (confirmed) are what's actually live as of 2026-08-22. Separately, the rerank endpoint's URL path for the (now-retired) `llama-3.2-...` model needed underscores (`llama-3_2-...`) while the JSON `model` field needed dots — a real dot-vs-underscore inconsistency in NVIDIA's own API, caught via a live 404 before it shipped.
- Wired into `pipeline/gap_challenger.py`'s search funnel: dedup → rerank → judge is now a real funnel (previously dedup → judge, with `judge_candidates()`'s 8-candidate LLM budget spent on whatever order the search APIs happened to return). Reranking is additive and fails soft — no API key, an HTTP error, or a timeout falls back to unranked dedup order, never breaks the funnel. Live-verified against a real gap and real Semantic Scholar/arXiv results: the genuinely relevant paper scored highest, an irrelevant control passage scored lowest. 15 new tests (8 in `tests/test_relevance_ranking.py`, 7 more in `tests/test_gap_challenger.py`). Full detail in RESUME.md.
- Epic 3.3's metadata-filtering gap is also now closed (2026-08-22, unrelated to the Qdrant blocker) — see RESUME.md. "Venue" filtering, mentioned in earlier notes here, was never actually specified in any planning doc and correctly wasn't built.

**Resolved, 2026-08-23 — Postgres set up with no Docker, same portable-binary pattern as ArcadeDB/JDK:**
- ~~Postgres (Phase 4, Epic 4.1 — Postgres Migration & Research Artifact Registry)~~ **User asked to start Phase 4 as the real prerequisite for a professional UI (Phase 5 is gated behind it).** [PostgreSQL](https://www.postgresql.org) has an official EnterpriseDB Windows **ZIP archive** (binaries only, no installer) — extract anywhere, `initdb` a data directory, `pg_ctl start`, no service registration, no admin rights. Downloaded PostgreSQL 18.6 to `C:\Users\Divya\tools\postgresql18\`, initialized a data directory, started on port 5433 (`bin\pg_ctl.exe -D <data dir> -l <logfile> -o "-p 5433" start`), created a dedicated `clinova_app` role + `clinova` database (not using the `postgres` superuser for the app). Confirmed working end-to-end: real `psycopg` connection, real JSONB round-trip (writes as a Python dict via `Jsonb()`, reads back as a native dict, no manual json.dumps/loads needed).
- `utils/database.py` rewritten entirely (psycopg instead of sqlite3) behind its exact pre-migration public function signatures — zero call-site changes needed anywhere else in the pipeline. New `migrations/*.sql` (forward-only, tracked in a `schema_migrations` table) replace the old ad hoc `CREATE TABLE IF NOT EXISTS` script. One real, deliberate improvement over the SQLite schema, not just a port: `runs.results_gz BLOB` (manually gzip-compressed) became `runs.results_json JSONB` (native — Postgres TOAST-compresses large JSON internally, so the manual gzip step was no longer doing useful work). A second real improvement: `papers.run_id`'s foreign key is now actually enforced (`ON DELETE CASCADE`) — SQLite declared the same FK but never enforced it (`PRAGMA foreign_keys` was never turned on), so `delete_run()` always had to manually pre-delete `papers` as a workaround; Postgres does the real cascade now.
- New Research Artifact Registry (`research_artifacts` table, FR-22) and Run Manifest recorder (`run_manifests` table, FR-23) — exact schemas from `06-versioning-lineage-architecture.md` §2/§3. `promote_artifact()` enforces the EXPERIMENTAL→CANDIDATE→CHAMPION→ARCHIVED lifecycle as a real, tested, rejected-on-violation state machine, not just documentation. `token_usage` is honestly `NULL` — no call site in this pipeline counts tokens yet, and nothing here fabricates a fake value to fill the field.
- **One-time real data migration, not just a schema port:** `scripts/migrate_sqlite_to_postgres.py` migrated all 5 real saved runs plus 187 real cache rows (LLM-derived wiki pages, evidence objects, Docling extractions, enriched references, gap validations) from the pre-existing `data/run_history.db` — verified every migrated run's data is dict-identical between the old and new backend before treating the migration as done. The old SQLite file was never modified or deleted (forward-only, per ADR-005/FR-21).
- **The ~14 existing tests that isolated themselves via a tmpdir SQLite file needed rewriting** — not mocked (a deliberate deviation from the original plan's "mock psycopg" idea): Postgres is now the app's one required datastore, same as SQLite always was, and this codebase's own established convention is to test the DB layer against a real (if temporary) database, not mocks. New `tests/pg_test_utils.py` gives each test class its own throwaway Postgres *schema* instead of a throwaway file — same full isolation, confirmed live (a key written in one schema does not leak into another). Two new test files (`tests/test_database_registry.py`, `tests/test_database_runs.py`, 41 tests) add real coverage for save_run/load_run/list_runs/delete_run and the new registry/manifest functions — genuinely untested before this pass, not just a migration-era gap. Full suite now 523 passing.
- **Wired into `app.py`:** every completed run now also records a `pipeline`-type `ResearchArtifact` and a full `RunManifest` (git commit, parser/reference-resolver/embedding/reranker/graph versions, quality-gate results, real wall-clock duration) — attempted for gate-blocked runs too, since a FAIL-gated run is itself a real research event worth recording. Failure here degrades to a warning, same convention as the ArcadeDB graph-persistence wiring. Live-verified: real migrated runs load correctly through the UI on the new Postgres backend, and the exact manifest-recording code path was exercised directly against the live database with real imported version constants (confirmed correct values for `embedding_model_version`/`reranker_version` etc.) before being treated as done — a full live pipeline run wasn't repeated for this specific check since the underlying LLM call sites were already extensively live-verified in Phases 1-3.
- **The server is a real, separate local process you now need to start manually** (`bin\pg_ctl.exe -D <data dir> -l <logfile> -o "-p 5433" start`, run from inside the extracted PostgreSQL distribution's `pgsql` directory) — unlike ArcadeDB/NVIDIA, this one is NOT optional: the whole app's save/load history depends on it being up.
- **Deferred, not attempted in this pass:** Epic 4.3 (Champion/Challenger Evaluation Harness & Benchmark Expansion) and Epic 4.4 (Lineage Views & Compare Engine) — both depend on the registry/manifest actually holding real data first, and both are large enough (4.3 needs to unify two incompatible benchmark case formats and add ~6 new case types; 4.4 is a UI-facing diff engine) to deserve their own dedicated pass. Full detail in RESUME.md.
