## Deferred from: code review of 2-3-cache-enriched-reference-metadata (2026-08-05)

- Title-only cache identity risks silent cross-reference collisions: two genuinely different papers sharing an exact title (surveys, common chapter titles, reprints) collide on the same `cache_key`; whichever is enriched first silently and permanently donates its DOI/abstract/authors to every other reference with that title. Fixing this needs author/year disambiguation added to the identity, which is a real design change beyond AC3's literal "DOI hash, else normalized-title hash" scope — needs a corresponding AC update, not a same-story patch.
- Ref-derived fallback fields (`year`, `authors` via `ref.get(...)`, and `arxiv_id`) get frozen into the cached entry at first-write time and replayed verbatim for every later reference sharing the same identity, even if a later citation's local data differs. Inherent to identity-keyed caching (the first successful resolution becomes canonical for that identity); narrow, low-severity, not fixable without abandoning simple identity-keyed caching.
- Time-varying fields (`citations`/`citationCount`, `open_access_url`) are baked into the same permanent cache entry with no TTL or per-field refresh — the only invalidation path is a full `REFERENCE_STAGE_VERSION` bump that wipes the entire table. Matches the 2026-08-04 `wiki_pages` entry's "cache growth/retention policy" item and AD-3's own version-bump-only invalidation design; not specific to this story.
- `get_cached_reference`/`save_cached_reference` (`utils/database.py`) call a full `init_db()` executescript on every invocation, with no connection reuse across the per-reference loop. Identical to the `parameters` table's identically-deferred finding (Story 2.2); same architecture Story 2.1 introduced.
- `get_cached_reference`/`save_cached_reference` have no `try/finally` around their SQLite calls (distinct from the `enrich_reference`-level guard this story's review added, which now swallows a broken cache and degrades to "no cache" at the call site) — an exception mid-call inside these two functions themselves still skips `conn.close()`. Identical to the 2026-08-04 `wiki_pages`/`parameters` entries; existing file-wide convention, not introduced by this story.
- `doi_or_title_hash` column is populated but never read back or verified by any test. Mirrors the `parameters` table's identically-deferred `content_hash`-write-only finding (Story 2.2).
- A reference that will never resolve (deleted preprint, unfixable title typo) pays the full 4-8-call API waterfall on every single future run, forever, since Tier-3 is never cached (correct per AD-2) — and nothing measures or surfaces this recurring cost. Matches the 2026-08-04 `wiki_pages` entry's "no cache hit/miss observability" item; no logging convention exists yet.
- `extract_and_enrich_references`'s in-run duplicate-skip normalization (`_norm`: lowercase + strip + truncate to 60 chars) and the new cross-run cache identity normalization (`title.lower()`, untruncated) are two different, unshared implementations of "same title." ## Deferred from: code review of 2-6-correct-arxiv-query-construction (2026-08-05)

- Stopword filtering under strict AND semantics — common filler words ("of", "in", "with") in a title+description query now must also match under `_build_arxiv_query`'s AND-join, trading the old false-positive problem for a potential false-negative (recall) problem on longer, stopword-laden queries. A genuine future quality refinement, but beyond AD-7's stated scope (fixing the OR-vs-AND grouping bug specifically).
- Duplicate terms in a query (e.g. "gene gene expression" → `all:gene AND all:gene AND all:expression`) are not deduplicated by `_build_arxiv_query`. Cosmetic redundancy, not a correctness bug.
- AND-joining makes the effective arXiv query string longer (each term carries a 4-char `all:` prefix plus ` AND `) with no check against any arXiv API query-length limit. No evidence of an actual limit being hit in practice; revisit if observed.
- `_build_arxiv_query`'s Lucene-character sanitization (colons/parens/quotes/boolean-operator-words) is a minimal, targeted set, not exhaustive Lucene-reserved-character escaping (`+`, `-`, `[`, `]`, `^`, `~`, `*`, `?`, `\` are not handled). The patched set covers the most likely and most dangerous cases from LLM-generated gap titles; full Lucene escaping is a broader, more open-ended defensive-programming task.
