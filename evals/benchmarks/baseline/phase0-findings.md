# Phase 0 Baseline Findings — Problems A-F against real data

Generated by `generate_baseline_report.py` running the **unmodified existing pipeline** against a real 3-paper corpus, plus one targeted diagnostic re-run (`diagnose_zero_gaps.py`) to pin down a live failure observed during the run. No engine code was changed to produce these findings.

## Headline finding: a live, reproduced instance of Problems C+F together

The baseline run's gap-detection stage returned **0 gaps** from `detect_gaps`. Re-running the identical stage against the identical saved wiki/graph/context (`diagnose_zero_gaps.py`) produced **5 well-evidenced, properly-grounded gaps** on the very next call — each citing real limitation/future-work text from the actual papers (e.g., "Analyses were restricted to cohorts of largely European ancestry, limiting generalizability to other ethnic groups").

**What this proves, concretely:**
- **Problem F (nondeterminism) is not theoretical** — identical input produced a 0-gap result once and a 5-gap result immediately after, from the same stage, same prompt, same model.
- **Problem A (silent data loss) compounds it** — `gap_detector.py`'s `json.loads` failure path (`pipeline/gap_detector.py`, `detect_gaps`) discards the raw LLM response on a parse failure with **no logging of what the raw response actually was**. This baseline run cannot tell us whether the original 0-gap result was a malformed-JSON response, a refusal, or a genuinely different (but valid) "no gaps" judgment — the evidence needed to distinguish those cases was never captured. This is the literal, real-world version of the inherited project's already-documented gap ("no cache hit/miss observability... no logging convention exists yet," `deferred-work.md`), now shown to also block root-causing the exact class of failure this whole platform exists to fix.
- **Problem C (fallback ≠ trusted) has a severe, previously-undocumented consequence downstream.** `generate_proposals` (`pipeline/proposal_generator.py` lines 42-49) has no guard for an empty `gaps` list: `actionable_gaps = [g for g in gaps if ...]` then `if not actionable_gaps: actionable_gaps = gaps` — when `gaps == []`, `actionable_gaps` stays `[]`, and the function **still calls the LLM** with an empty "Validated Research Gaps: []" section in the prompt, instructing it to "Generate 3-5 concrete research paper proposals" regardless. The LLM complied: **this baseline run produced 4 specific, plausible-sounding research proposals** (e.g., "Mendelian Randomization of Brain Imaging Phenotypes to Elucidate Causal Pathways Underlying Co-occurring Autism and ADHD") **with zero grounding in any validated gap** — because there were no validated gaps to ground them in. A user looking at this report would see 4 confident, specific proposals with no visible indication they were fabricated from nothing.

This is materially worse than the brief's stated Problem D ("no search results" silently read as "gap is open") — it is "**no gaps at all** silently read as 'here are 4 concrete research directions.'" Recorded as the **highest-priority Benchmark v1 case** (see below), and as direct, real justification for `04-ai-research-architecture.md` §5's Gap Challenger state machine and PRD FR-12's binding rule that empty/failed upstream results must never silently present as confident output.

## Problem B (reference contamination) — a live instance found, not hypothesized

Scanning the run's 82 enriched references for near-duplicate titles surfaced:

- **Three exact-DOI duplicate pairs never merged**: e.g. "Autism spectrum disorder" (DOI `10.1038/s41572-019-0138-4`) appears as two separate entries in `ref_papers` because two different source papers in the corpus cite it. **The existing pipeline has no canonical-identity merging at all today** — this isn't a wrong-merge risk (the Story 2.3-documented title-collision risk from the inherited codebase), it's the more basic finding that *no merging of any kind happens*, confirming `05-data-architecture.md` §5's canonical resolution architecture addresses a real, currently-100%-unaddressed gap, not a partially-addressed one.
- **A genuinely contaminated reference**: "Español Santillana by Paloma Lapuerta et al." (a Spanish-language textbook, DOI `10.1353/hpn.2017.0025`) appears **three times** in the AuDHD neuroimaging reference corpus — a citation entirely unrelated to the domain, almost certainly a citation-parsing/metadata-matching artifact from a garbled or truncated raw citation string. This is Problem B made concrete: an unrelated paper has entered the trusted reference corpus with no flag distinguishing it from a real citation.
- **Truncated/malformed DOIs on "Unknown"-titled entries**: three references have `title: "Unknown"` paired with visibly truncated DOI strings (`10.3233/jad-`, `10.1016/j`, `10.1186/s13229-`) — a live instance of Problem A (extraction data loss) at the DOI-parsing level specifically.
- **Character-encoding corruption**: an en-dash in a title ("1980–2013") was corrupted to a replacement character ("1980�2013") during extraction — a minor but real Problem A instance worth folding into the multi-parser reconciliation's completeness scoring (`05-data-architecture.md` §3-4).

## Problem E (graph quality) — baseline is currently invisible, but healthy this run

`build_knowledge_graph` reported `fallback_used=None` (i.e., the real LLM-based graph build succeeded, no fallback triggered) with 96 entities and 95 relationships from 3 papers. No version, quality score, coverage, duplicate-rate, or unresolved-entity-rate is computed anywhere in the baseline — confirming `05-data-architecture.md` §9's assessment that this is genuinely greenfield work, not a partial fix. This run's healthy `fallback_used=None` result is itself useful as a "known-good" comparison point once Phase 3's quality scoring exists.

## Problem D (search-result-as-open) — not exercised this run

`validate_gaps` never ran against a non-empty gap list in this run (0 gaps in, 0 gaps out — see headline finding), so no direct evidence either way was produced for Problem D specifically. Re-run against `diagnose_zero_gaps.py`'s 5 recovered real gaps is a natural Phase 0 follow-up if a second baseline data point is wanted, but is not required to proceed to Phase 1.
